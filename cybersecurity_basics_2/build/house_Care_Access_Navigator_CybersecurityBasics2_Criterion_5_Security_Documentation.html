5. Effective Security Documentation

5.1 Procedure for a security control implementation: PROC-SEC-03

PROC-SEC-03 Linux server SSH hardening

ControlStrong authentication for server access (POL-SEC-01 sections 2.3 and 4.5)
StandardsNIST CSF 2.0 PR.AA-03; ISO/IEC 27001 A.8.5; HIPAA 164.312(d); CIS Debian benchmark (SSH section)
OwnerIT-Support (servers), verified by the Security Analyst
First implemented2026-11-19 on hrmc-linux-srv01 (case CB2-2026-001)
Purpose

Stop password guessing against servers, show the system-use policy at every login and keep a record that the control works.

Before you start
  • Make sure every person who needs access has an SSH key installed (step 2), or you will lock them out.
  • Keep a second session open while you change the configuration.
Steps
  1. Back up the configuration. cp -a /etc/ssh /root/ssh-backup-$(date +%F)
  2. Install keys for approved users. Add each user's public key to ~/.ssh/authorized_keys; folder permission 700, file 600, owned by the user.
  3. Create the banner. Put the approved system-use text in /etc/issue.net (file lab/system_use_banner.txt).
  4. Add the hardening file /etc/ssh/sshd_config.d/10-hrmc-hardening.conf:
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
MaxAuthTries 3
LoginGraceTime 30
Banner /etc/issue.net
  1. Validate before applying. sshd -t must print nothing. If it shows an error, fix it and do not continue.
  2. Apply. Reload sshd (systemctl reload ssh, or kill -HUP $(cat /run/sshd.pid) on hosts without systemd).
  3. Verify (all must pass):
    • sshd -T | grep -E 'passwordauthentication|permitrootlogin|maxauthtries|banner' shows the values above
    • a password login is refused: Permission denied (publickey)
    • a key login works and shows the banner
    • Wazuh shows the successful key login (rule 5715) for the test user
  4. Record. Save the transcript, add it to the change ticket or incident case, and update the asset record.
Roll back

Copy the backup from step 1 back to /etc/ssh, run sshd -t, then reload.

Evidence from the first run

cybersecurity_basics_2/evidence/remediation_transcript.txt: password login refused, key login with banner, tjones

locked, effective settings listed.

5.2 Step-by-step guide for a security task: GUIDE-SEC-01 incident reporting

GUIDE-SEC-01 How to report a security incident (all staff)

Use this guide if you think something is wrong: a strange email, a lost device, someone using your account, patient

data sent to the wrong person, or a warning on your screen. Report first; you do not need to be sure.

Step by step
  1. Stop and don't make it worse. Don't click anything else, don't delete the email or file, don't turn the computer off. If you think your password is known, do not keep using the account.
  2. Disconnect if told to, or if it is obvious. If files are being encrypted or the screen asks for ransom, unplug the network cable or turn Wi-Fi off. Leave the computer on.
  3. Report straight away, within 15 minutes:
    • phone the Service Desk security line (ext. 4357, option 9), 24 hours a day, or
    • email security@hrmc.lab (only if email still works and is not the problem).
  4. Say what you saw: your name and department, the computer or device name (on the sticker), what happened and when, what you clicked or typed, and whether patient or payment data might be involved.
  5. Write it down while you remember: times, screen messages (a phone photo of the screen is fine), the email subject.
  6. Follow the instructions from the Security Analyst. They may ask you to change your password, keep the device for collection, or not discuss the incident.
  7. Keep it confidential. Don't post about it or forward the suspicious email to colleagues.
What happens next

The SOC opens a case (for example CB2-2026-001), sets a severity, and contains and investigates it under the incident

response plan (IRP). If patient data may be involved, the Privacy Officer assesses whether a HIPAA breach notification is needed.

You will be told when the case is closed.

You will never get in trouble for reporting in good faith.

5.3 Security playbooks: two incident scenarios

PB-01 Playbook: account compromise (password guessing, credential theft)

TriggersWazuh 5763 / 5551 (SSH brute force), 40112 (failures then success), 100502 / 100507 (Keycloak guessing then success), 100602 / 100604 (Windows guessing, RDP from outside)
Default severitySEV-3 if all attempts failed; SEV-2 if a login succeeded; SEV-1 if ePHI was then accessed
OwnerTier 1 SOC analyst; Tier 2 / Incident Commander for SEV-1/2
ExampleCB2-2026-001 (tjones on hrmc-linux-srv01, closed 2026-11-19); SOC1-2026-001 (test.nurse2)
1. Identify (0-15 min)
  1. Open a case in the tracker (irtrack.py new), with the alert IDs and times.
  2. Confirm in the dashboard: source IP, target account, number of failures, and whether a success followed from the same source.
  3. Check whether the source is internal, a known scanner or an approved test (false positive), or outside / unknown.
  4. Look for what happened after the success: sudo, file changes (FIM), outbound connections, record access.
2. Contain (15-60 min)
  1. Lock or disable the account (Linux passwd -l, Keycloak / Entra: disable and revoke sessions).
  2. Block the source IP at the firewall or in the IdP.
  3. Preserve evidence first: export the alerts and logs and hash them.
3. Eradicate
  1. Reset credentials; require MFA for the role.
  2. Remove the weakness that allowed guessing (servers: PROC-SEC-03 keys-only SSH).
  3. Remove persistence: new keys in authorized_keys, cron jobs, new users.
4. Recover
  1. Re-enable the user only after the HR / manager check and a new credential.
  2. Re-test: the old password is refused, legitimate access works, monitoring still sees the host.
5. Close and learn

Record the timeline, actions and evidence; write at least 2 lessons; tune rules if they were noisy or late.

PB-02 Playbook: suspected data exfiltration from ePHI stores

TriggersWazuh 100612 (mass EHR export reads), 100651 (mass reads then connection to a bad address), 100630 / 100621 (connection to a known-bad address), FIM 553 / 554 / 550 on ePHI folders, 100522 (bulk EHR access)
Default severitySEV-1 if ePHI may have left HRMC; SEV-2 if it was staged but not sent
OwnerIncident Commander; Privacy Officer from the start
ExampleCB2-2026-002 (staging on hrmc-linux-srv01, closed 2026-11-19); SM1-SCN-01 (rclone to 203.0.113.77)
1. Identify (0-15 min)
  1. Open a SEV-1/2 case and page the Incident Commander and Privacy Officer.
  2. Establish what data: which files or records (FIM paths, 4663 object names, EHR patient IDs), how many, which classification.
  3. Establish where to: destination IP and port, process (rclone.exe, nc, scp), user.
  4. Establish when: first read, staging, transfer (correlated alerts give the timeline).
2. Contain
  1. Block the destination at the egress firewall; isolate the host if transfer is still running.
  2. Disable the user account involved (PB-01 steps).
  3. Preserve evidence: copy staged files to the evidence store and hash them before removing anything.
3. Eradicate
  1. Remove staged copies and tools (rclone), restore deleted or changed files from the known-good copy, and verify hashes.
  2. Close the path: egress allow-list, remove the role's access to the data, approval for bulk exports.
4. Recover
  1. Verify integrity of the store (hashes match), FIM back to normal, monitoring active.
  2. Watch the user, host and destination closely for 30 days.
5. Notify and learn
  1. Privacy Officer runs the HIPAA four-factor breach risk assessment; notices within 60 days if required (72 h for EU data).
  2. Lessons and rule tuning recorded in the case.

A third playbook with six runbooks (CAN-IR-PB-02, Incident Response 1) is in the knowledge base as PB-03.
