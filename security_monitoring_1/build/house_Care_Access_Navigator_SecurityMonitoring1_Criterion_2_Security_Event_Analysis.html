2. Security Event Analysis

2.1 Log types and how to read them

Log typeKey fieldsWhat to look for
Windows Security logevent_id, target_user, logon_type (2 local, 3 network, 10 RDP), ip, status (0xC000006A = bad password), object_name, access_mask (0x1 = read), application, dest_ipFailures before a success; RDP from outside 10.x; reads on sensitive shares; unusual programs (rclone.exe) talking to the internet
Linux auth.log (syslog)timestamp, host, program[pid], message: Failed / Accepted password for USER from IPMany failures from one source, then Accepted from the same source
Wazuh FIMfile path, event (added / modified / deleted), mode realtime, checksumsChanges in folders holding ePHI, outside change windows
Command output (outbound_tcp)local_ip:port -> remote_ip:portConnections to addresses that are not the hospital or its suppliers
Keycloak / EHR (JSON)type, error, username, ip, client / role, patient_id, actionRole and action mismatch (billing opening charts), volume, source IP

Interpretation methodology: (1) identify the source and its schema; (2) normalise time to UTC and the user to the IAM username; (3) compare with the baseline (section 3.5); (4) group by user, host and source IP; (5) look for sequence (fail → success → access → transfer); (6) confirm across a second source before escalating.

Validation finding: on the first run rule 100650 did not fire. The manager log showed "Signature ID '100521' was not found ... Rule '100650' will be ignored": Wazuh loads rule files alphabetically, so sm1_rules.xml loaded before soc1_rules.xml and referred to a rule that did not exist yet. Renaming the file to zz_sm1_rules.xml fixed the order (enabled rules 7,033 → 7,034) and the re-run fired 100650. Lesson: every new rule is tested end to end, not just loaded.

2.4 Complete incident detection scenario: SM1-SCN-01

Story: an attacker guesses the password of a Linux user and of the billing account test.billing1, logs in to the billing workstation by RDP from outside, reads 30 EHR export files with rclone.exe, sends them to 203.0.113.77 and opens patient charts in the EHR.

First alert of each level-10+ rule. 100650 appears at minute 5.6 because it fired in the re-run after the load-order fix (section 2.3).

Conclusions: (1) the same attacker is visible in four sources within six minutes; (2) every step was detected, the highest alerts (100651 level 15, 100650 level 14) pointed straight at data exfiltration and patient-record misuse; (3) 30 EHR export files and the charts SYN-PT-30500 to 30515 must be treated as exposed, which starts the HIPAA breach risk assessment; (4) root causes: password-only RDP from the internet and a billing role able to read clinical data.
